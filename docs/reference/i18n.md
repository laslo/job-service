# Internationalization (i18n)

---

## Product assumptions (MVP)

- **Locales:** **2–3 languages**, including **English** and **Spanish** (third locale optional).
- **Not required for MVP:** RTL, hieroglyph-heavy scripts, or CJK-specific line-breaking concerns—keep catalogs and layout simple until product expands.
- **Rendering:** Prefer **React Server Components (RSC)** and the **App Router** for productivity and fewer client bundles.

---

## What “good” looks like with RSC + App Router

- **Locale in the URL** (e.g. `/en/...`, `/es/...`) or a single prefix segment so caches and links are explicit.
- **Server components** load the right messages **on the server** for the active segment; avoid shipping all languages to the client unless a slice truly needs client interactivity.
- **Type-safe** message keys (or generated types) so refactors do not silently break UI copy.
- **Colocation:** translations live near features or in a dedicated `messages/` tree—pick one convention and stick to it across apps in the monorepo.

---

## Library and pattern alternatives

### 1. next-intl (App Router–oriented)

- **Fit:** Strong story for **App Router**, layouts, and server components; widely used with Next 13+.
- **Pros:** Practical defaults, middleware for locale detection, good docs for RSC patterns.
- **Cons:** Learn its provider boundaries for the small amount of client UI you still have.

### 2. Paraglide (inlang) + Next

- **Fit:** **Compile-time** message inlining / tree-shaking emphasis; TypeScript-friendly.
- **Pros:** Excellent **DX for types** and dead-code elimination of unused strings.
- **Cons:** Slightly different toolchain than “JSON files only”; team onboarding curve.

### 3. Lingui

- **Fit:** Macro-based extraction, ICU messages, works with RSC with some setup.
- **Pros:** Mature ICU formatting; good for larger catalogs.
- **Cons:** More moving parts for a small MVP than next-intl if you stay mostly in RSC.

### 4. next-i18next (Pages Router legacy)

- **Fit:** Historically the default for **Pages Router**.
- **Cons:** For an **RSC-first App Router** greenfield, this is usually the wrong default—maintainers steer new projects to App Router–native libraries.

### 5. Lightweight custom (JSON + small helper)

- **Fit:** Tiny apps with almost no client copy.
- **Cons:** You reinvent typing, loading, fallbacks, and plural rules—usually not worth it once you have **2+ locales** and shared packages.

---

## Alternative “architecture” choices (not just libraries)

| Approach | Description | Trade-off |
|----------|-------------|-----------|
| **Per-request server messages** | RSC loads catalog for `locale` from params | Best alignment with RSC; watch caching boundaries for high-traffic pages. |
| **Client-heavy i18n** | Send all messages to the client | Simpler for highly interactive SPAs; **worse** for RSC-first and bundle size. |
| **Shared package across apps** | `packages/i18n` consumed by marketing + app | Great for monorepo; requires a **single** locale routing convention across apps ([`decisions/alternatives.md`](../decisions/alternatives.md) — planned apps). |

---

## Recommendation (this repo)

Use **next-intl** with **App Router** locale segments and **RSC-first** message loading. Revisit **Paraglide** if compile-time inlining and stricter key typing become the bottleneck.

Document the chosen locale list and URL strategy in the root app’s README when scaffolding.
